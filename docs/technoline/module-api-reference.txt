 סקירה כללית — מה זה בכלל?
 ה-API של המרכזיה מאפשר לשלוט על שיחות טלפון באופן תכנותי .
 כשמתקשר נכנס לשלוחה — המרכזיה שואלת את השרת שלכם מה לעשות,
 והשרת מחזיר הוראות בפורמט JSON.
 🔒 נתונים רגישים — חובה לקרוא לפני איסוף פרטי אשראי / CVV / ת.ז. 
 כל קלט שהמתקשר מקיש נשמר בלוג ה-API ( ivrApiLog ) כחלק מכתובת ה-URL. כדי שלא יישמר נתון רגיש בלוג —
 הוסיפו "maskLog": true לאלמנט הקלט ( getDTMF / simpleMenu / record / stt ).
 הערך המלא נשלח לשרת שלכם כרגיל (כדי שתוכלו לסלוק/לעבד) — רק העותק שנשמר בלוג ממוסך:
 2 תווים ראשונים + 2 אחרונים והשאר XXXX (קלט קצר עד 4 תווים — התו הראשון בלבד).
 דוגמה: כרטיס 1234567890123456 → לשרת נשלח מלא, בלוג נשמר 12XXXX56 ; ‏CVV 123 → בלוג 1XXXX .
 — פירוט ודוגמה מלאה: מודול קבלת הקשות (getDTMF) . 
 במילים פשוטות: המרכזיה = הטלפון. השרת שלכם = המוח.
 המרכזיה שואלת "מה לעשות?", השרת עונה ב-JSON, המרכזיה מבצעת.
 דוגמה פשוטה לתרחיש
 1
 לקוח מתקשר
 לקוח חייג למספר שלכם ונכנס לשלוחה במרכזיה.
 2
 המרכזיה פונה לשרת שלכם
 המרכזיה שולחת בקשת GET לכתובת שהגדרתם, עם פרטי השיחה כפרמטרים ב-URL.
 3
 השרת שלכם מגיב ב-JSON
 השרת מחזיר הוראות — למשל "הנגן הודעה ובקש ספרת בחירה מהמתקשר".
 4
 המרכזיה מבצעת ומדווחת
 המרכזיה מבצעת, ואז פונה שוב לשרת עם התוצאה — מה המתקשר הקיש, מה הוקלט וכו'.
 חשוב: אם השרת לא מחזיר JSON תקין המתאים לאחד המודולים —
 המתקשר יוחזר אוטומטית לתפריט הקודם.
 תרשים זרימה — מחזור חיי שיחה
 מתקשר חייג 
 נכנס לשלוחה 
 →
 מרכזיה → שרת 
 GET עם פרמטרי שיחה 
 →
 שרת → מרכזיה 
 JSON עם הוראות 
 →
 מרכזיה מבצעת 
 מנגן / מקליט / מנתב 
 →
 מרכזיה → שרת 
 GET עם תוצאה 
 דוגמה מעשית — URL שמגיע לשרת שלכם
 https://yourserver.com/api/pbx?PBXphone=0501234567&PBXnum=035001234&PBXcallId=ABC123&PBXcallStatus=CALL&PBXextensionId=5
 השרת שלכם עונה:
 // JSON פשוט — בקשת ספרת בחירה 
{
 "type" : "getDTMF" ,
 "name" : "userInput" ,
 "max" : 1 ,
 "files" : [
 { "text" : "הקישו 1 למכירות, 2 לתמיכה" }
 ]
}
 המרכזיה מבצעת ופונה שוב לשרת עם התוצאה:
 https://yourserver.com/api/pbx?PBXphone=0501234567&...& userInput=1 
 שם הפרמטר = ערך name שהגדרתם! 
 שלחתם "name": "userInput" → התוצאה תגיע כ- userInput=1 ב-URL.
 פרמטרים קבועים — מה המרכזיה שולחת תמיד
 בכל פנייה מהמרכזיה לשרת שלכם, הפרמטרים הבאים מצורפים ל-URL אוטומטית:
 PBXphone
 מספר הטלפון של המתקשר (הלקוח)
 PBXnum
 המספר הראשי של המרכזיה שלכם — קבוע לכל השיחות. לזיהוי המספר הספציפי שאליו חייגו (כשיש כמה מספרי גישה) השתמשו ב-PBXdid
 PBXdid
 המספר שאליו חייגו — רלוונטי כשיש כמה מספרי גישה למרכזיה
 PBXcallId
 מזהה ייחודי לכל שיחה — שמרו אותו ב-DB לצורך מעקב
 PBXcallType
 מקור השיחה:
 in שיחה נכנסת  
 out יוצאת / קמפיין
 PBXcallStatus
 סטטוס השיחה:
 CALL בשיחה כרגע  
 HANGUP ניתוק
 PBXextensionId
 מזהה השלוחה הנוכחית
 PBXextensionPath
 נתיב השלוחה (היררכיה של שלוחות)
 טיפ: PBXcallStatus=HANGUP מגיע גם לאחר ניתוק.
 זה הרגע לבצע פעולות סיכום — שמירה ב-DB, שליחת מייל וכו'.
 שיחה מופנית — "מפנה השיחה"
 כאשר מנוי מפנה את הקו שלו למרכזיה (הפניה קבועה, בתפוס או באין-מענה), מספר המתקשר
 ב- PBXphone נשאר של המתקשר המקורי — ולכן בלעדיו אי אפשר לדעת
 לאיזה קו הוא בעצם חייג . במקרה כזה המרכזיה מצרפת גם את הפרמטרים הבאים.
 שיחה שלא הגיעה מופנית פשוט לא תקבל אותם כלל (ולא ערכים ריקים).
 PBXdiversion
 המספר שממנו הופנתה השיחה — הקו שהמתקשר חייג אליו בפועל
 PBXdiversionReason
 סיבת ההפניה:
 unconditional הפניה קבועה  
 user-busy תפוס  
 no-answer אין מענה  
 unavailable לא זמין
 PBXdiversionName
 שם התצוגה של המפנה — נשלח רק אם הספק סיפק אותו
 PBXdiversionCounter
 מספר ההפניות בשרשרת (1 = הופנה פעם אחת)
 PBXdiversionPrivacy
 האם המפנה ביקש להסתיר את זהותו ( full / off )
 PBXdiversionChain
 שרשרת מלאה של מפנים, מופרדת בפסיקים — רק כשהיו כמה הפניות.
 הראשון ברשימה הוא המפנה הישיר
 https://yourserver.com/api/pbx?PBXphone=0501234567&PBXdid=0765673724&PBXdiversion=548466096&PBXdiversionReason=unavailable&PBXdiversionCounter=2
 שימוש אופייני: עסק שמפנה כמה קווים לאותה מרכזיה יכול לזהות לפי
 PBXdiversion לאיזה סניף / מחלקה הלקוח התכוון, ולהחזיר תפריט או שיוך שונה —
 בלי להקים שלוחה נפרדת לכל קו.
 ניהול ה-REQUEST — ערכים קבועים וניקוי
 בנוסף לפרמטרי המערכת ולערכים שהמתקשר מזין, ניתן לצרף ערכים קבועים משלכם 
 לכל פנייה לשרת, וכן להסיר ערכים מה-REQUEST המצטבר.
 שני אלה אינם סוג תגובה ( type ) — הם ערכים כלליים :
 ניתן להגדיר אותם בהגדרות השלוחה (תקפים לאורך כל חיי השיחה), או לשלוח אותם
 בתוך כל תגובה כדי לעדכן אותם תוך כדי תנועה.
 שיטת שליחה — GET (ברירת מחדל) / POST
 כברירת מחדל כל פנייה נשלחת ב- GET : כל הפרמטרים (מערכת + הקלט המצטבר) יושבים
 במחרוזת ה-URL אחרי ה- ? , מופרדים ב- & — כולל ערכים שחוזרים על עצמם.
 זו הצורה הקיימת ואינה משתנה כלל .
 ניתן לבחור לשלוח ב- POST בשתי דרכים:
 איפה איך תחולה 
 בהגדרת השלוחה "method": "POST" (או "post": true ) כל השיחה ב-POST מההתחלה 
 בתשובת ה-API — נקודתית לערך "post": true על אלמנט (למשל getDTMF של אשראי) מהקריאה החוזרת ואילך, ו נשאר עד סוף השיחה (דביק) 
 ב-POST אותם פרמטרים בדיוק (כולל כפילויות מפתח והסדר) עוברים ממחרוזת ה-URL אל
 גוף הבקשה ( application/x-www-form-urlencoded ). הכתובת שהגדרתם — עם ה-query שלה —
 נשארת ב-URL; קִראו את הפרמטרים מ- $_POST (או $_REQUEST ).
 לנתונים רגישים: POST מונע מהערך להופיע ב-query של ה-URL (ולכן גם ב-access-logs של
 שרתי-web/proxy). מומלץ לשלב עם maskLog : POST מוציא את הערך מה-URL,
 ו- maskLog ממסך אותו גם בלוג המרכזיה.
 // getDTMF של אשראי — POST נקודתי + מיסוך בלוג 
{
 "type" : "getDTMF" ,
 "name" : "cardNumber" ,
 "max" : 16 ,
 "post" : true , // הקריאה החוזרת (ואילך) תישלח ב-POST 
 "maskLog" : true // וגם תמוסך בלוג 
}
 addParams — ערכים קבועים שמצורפים ל-URL
 מערך של מפתח=ערך שמצורף ל- כל פנייה לשרת.
 שימוש נפוץ: דגלים קבועים לשמירת מיקום בשיחה (למשל שלב בתהליך, מזהה תהליך וכו').
 הערכים האלה נשמרים כפרמטרים קבועים — הם נשלחים בכל
 callback , שורדים ניקוי REQUEST 
 (כולל clearRequest של החלפת לינק ), ואינם נמחקים בין הפניות.
 שליחה חוזרת של אותו מפתח מעדכנת את הערך (לא מוסיפה כפילות).
 removeParams — מפתחות לניקוי מה-REQUEST
 מערך של שמות מפתחות שיוסרו מה-REQUEST המצטבר מכאן והלאה.
 ההסרה חלה רק על הערכים שבשליטתכם (ערכי המתקשר, פרמטרים קבועים וקבועי השלוחה) —
 פרמטרי המערכת ( PBX... ) ופרמטרי הכתובת המקוריים תמיד נשמרים.
 פורמטים נתמכים
 שני השדות מקבלים מספר פורמטים (לבחירתכם):
 // addParams — אובייקט מפתח=ערך 
 "addParams" : { "pos" : "step3" , "flow" : "A" }
 // addParams — מערך זוגות 
 "addParams" : [{ "key" : "pos" , "value" : "step3" }]
 // removeParams — מערך מפתחות 
 "removeParams" : [ "otp" , "tmp" ]
 דוגמה — קביעת דגל מיקום בלי להחליף לינק:
 {
 "type" : "changeUrl" ,
 "clearRequest" : "no" , // לא לנקות — רק לעדכן דגלים 
 "addParams" : { "pos" : "menu_main" },
 "removeParams" : [ "otp" ] // להסיר ערך שכבר נצרך 
}
 מעתה כל פנייה תכלול את הדגל הקבוע:
 ...&PBXcallId=...& pos=menu_main &...
 systemMessages — החלפת הודעות מערכת לאורך השיחה
 גם זה ערך כללי (לא type של מודול): מאפשר להחליף הודעות מערכת 
 (קודי S... כמו הקראות מודול הסליקה, הודעות שגיאה וכו') בתוכן משלכם — לאורך כל המשך השיחה .
 כל קוד הודעת מערכת ממופה ל מערך קבצים זהה בדיוק למערך הקבצים הרגיל ( files ) —
 עם כל סוגי הערכים: name (קובץ), text (TTS), SF (הודעת מערכת אחרת),
 number , digits , sum , fileLink וכו'.
 ההחלפה תקפה מרגע שליחתה ועד סוף השיחה (או עד החלפה נוספת).
 שליחת קוד עם מערך ריק מחזירה אותו להודעת המערכת המקורית מה-DB.
 פורמטים נתמכים
 // מפה: קוד => מערך קבצים 
 "systemMessages" : {
 "S3008" : [{ "text" : "כמה תשלומים תרצה לפרוס?" }],
 "S3013" : [{ "name" : "thanks_custom" }, { "SF" : "S3014" }]
}
 // או מערך אובייקטים: { sm, files } 
 "systemMessages" : [
 { "sm" : "S3008" , "files" : [{ "text" : "כמה תשלומים?" }] }
]
 // החזרה להודעת ברירת המחדל — מערך ריק 
 "systemMessages" : { "S3008" : [] }
 שתי דרכי שליחה
 // 1) אלמנט עצמאי — חובה type:"systemMessages" 
{
 "type" : "systemMessages" ,
 "systemMessages" : { "S3008" : [{ "text" : "כמה תשלומים?" }] }
}
 // 2) מצורף ישירות למודול — נקבע *לפני* שהמודול רץ 
{
 "type" : "creditCard" ,
 "sum" : 250 , "payments" : 3 , "terminal" : "42" ,
 "systemMessages" : { "S3008" : [{ "text" : "בחר/י מספר תשלומים" }] }
}
 אלמנט עצמאי חייב לכלול "type": "systemMessages" (ככל תגובת Module API שחייבת type ).
 בלי type מוכר — המתקשר נשלח חזרה לתפריט הקודם.
 המודולים — כל ההוראות שניתן לשלוח
 כל תגובה מהשרת חייבת לכלול "type" המציין איזה מודול להפעיל.
 המודולים מסודרים לפי הגיון שימוש: מהשמעה בלבד ← אינטראקציה ← ניתוב ← ניווט ← סיום.
 הודעה פשוטה
 type: "simpleMessage" 
 מודול ה הפשוט ביותר — משמיע את קבצי ה- files שהגדרתם,
 ועובר מיד לפקודה הבאה בתור (או לפנייה הבאה לשרת).
 אין קלט, אין אינטראקציה, אין ערך מוחזר. 
 כללי ההשמעה זהים ל- simpleMenu — ניתן להשתמש בכל סוגי קבצי השמע
 כולל טקסט, מספר, ספרות ולינק חיצוני.
 פרמטר חובה? הסבר 
 type חובה "simpleMessage" 
 files חובה קבצי שמע להשמעה — ראו מקטע "קבצי שמע" 
 דוגמה:
 {
 "type" : "simpleMessage" ,
 "files" : [
 { "text" : "תודה על פנייתך, נציג יחזור אליך בהקדם" }
 ]
}
 אין תגובה חזרה לשרת. המרכזיה מנגנת ועוברת לפקודה הבאה בשרשרת,
 או לפנייה הבאה אם אין יותר פקודות.
 חסימה / ביטול חסימה מקבלת הודעות
 type: "messageConsent" 
 מאפשר לשרת שלכם לחסום או לבטל חסימה של קבלת הודעות מהמערכת עבור מספר —
 ישירות מתוך זרימת ה-API, למשל בתום שיחה שבה הלקוח ביקש להסיר את עצמו, או להיפך לאשר קבלה מחדש.
 כל פעולה נרשמת ב היסטוריית המספר (מי, מתי, מאיזה מקור).
 רמות: ניתן לחסום "level":"general" (חסימה כללית — מכל ההודעות),
 או רמה מסוימת "1" / "2" / "3" שהוגדרה במערכת. חסימה כללית גוברת על הכל.
 פרמטר חובה? הסבר 
 type חובה "messageConsent" 
 action רשות "block" (ברירת מחדל) או "unblock" 
 level רשות "general" (ברירת מחדל) / "1" / "2" / "3" 
 phone רשות המספר לחסימה. ברירת מחדל — המתקשר הנוכחי 
 files רשות הודעת אישור להשמעה לאחר הפעולה 
 דוגמה:
 {
 "type" : "messageConsent" ,
 "action" : "block" ,
 "level" : "general" ,
 "files" : [
 { "text" : "הוסרת מרשימת הדיוור, לא תקבל/י הודעות נוספות" }
 ]
}
 אלמנט שירות — לאחר הביצוע השיחה ממשיכה כרגיל (וניתן לצרפו לאותה תשובה עם מודולים אחרים).
 אישור / הסרה מקבלת צנתוקים
 type: "rhConsent" 
 מפעיל מתוך זרימת ה-API את דיאלוג ההסכמה לקבלת צנתוקים (קמפיין צלצול בלבד) —
 בדיוק כמו שלוחת "אישור / הסרה מקבלת צנתוקים" במרכזיה. המערכת בודקת את המספר שממנו המתקשר חייג 
 ברשימת "מאושרים לצנתוק" של המערכת ומציעה לו את הפעולה המתאימה:
 לא רשום — מושמע: "לאישור קבלת צנתוקים הקש 1". הקשה 1 רושמת את המספר.
 רשום — מושמע: "מספרכם רשום לקבלת צנתוקים. להסרת מספרכם מקבלת צנתוקים הקש 2". הקשה 2 מסירה.
 מקש אחר אינו נקלט. ללא הקשה (אחרי times חזרות) — השיחה ממשיכה בלי שינוי ברשימה.
 הודעת ההסכמה קבועה ואינה ניתנת להחלפה — לא דרך files ולא דרך systemMessages .
 ניתן להשמיע הודעת הקדמה משלכם במודול simpleMessage לפני המודול הזה.
 רק הודעות התוצאה (אושר / כבר רשום / הוסר / חסום) ניתנות לעריכה בהודעות המערכת.
 רק המתקשר רושם את עצמו. אין פרמטר phone ואין דרך להוסיף מספר לרשימה מהשרת —
 ההסכמה חייבת להינתן בהקשה של בעל המספר. מספר שמנהל המערכת חסם ישמע את הצעת האישור, אך הקשה 1 לא תבטל את החסימה
 (תוחזר blocked ) — חסימה מתבטלת רק בממשק הניהול.
 פרמטר חובה? הסבר 
 type חובה "rhConsent" 
 name רשות שם הפרמטר שיחזור לשרת. ברירת מחדל: rhConsent 
 times רשות כמה פעמים לחזור על ההודעה בהמתנה להקשה. ברירת מחדל: 3 , מקסימום 9 (ערך גבוה יותר נחתך ל-9) 
 מה חוזר לשרת (בקריאה הבאה):
 פרמטר ערכים הסבר 
 <name> approved / already / removed / none / blocked / invalid / timeout 
 תוצאת הדיאלוג: נרשם עכשיו / היה רשום / הוסר / לא היה רשום להסרה / חסום על ידי המנהל / אין מספר מזוהה / לא הוקש 
 STATUS_<name> approved / blocked / none מצב המספר ברשימה בסיום הדיאלוג 
 OFFERED_<name> approve / remove איזו אפשרות הושמעה למתקשר 
 דוגמה:
 [
 {
 "type" : "simpleMessage" ,
 "files" : [ { "text" : "שלום, ניתן להירשם לקבלת עדכונים בצנתוק" } ]
 },
 {
 "type" : "rhConsent" ,
 "name" : "consent" ,
 "times" : 2 
 }
]
 ואל השרת יחזור, למשל: consent=approved&STATUS_consent=approved&OFFERED_consent=approve 
 אלמנט שירות — לאחר הדיאלוג השיחה ממשיכה כרגיל. מספר מאושר נשלח בקמפייני צנתוק של המערכת ללא תלות ברשימת תפוצה, ומספר חסום מוסר מהשיגור.
 תפריט פשוט
 type: "simpleMenu" 
 מנגן הודעה ומחכה שהמתקשר יקיש מקש אחד בלבד מתוך רשימה מוגדרת מראש.
 מתאים לתפריטים כמו "הקישו 1 למכירות, 2 לתמיכה".
 הקשה על מקש שלא ב- enabledKeys — לא עושה כלום. המתקשר ממשיך להמתין.
 פרמטר חובה? ערכים הסבר 
 type חובה "simpleMenu" סוג המודול 
 name חובה שם כלשהו שם הפרמטר שיחזור עם ההקשה. לדוגמה "menuChoice" → יחזור menuChoice=2 
 enabledKeys חובה "1,2,3" מקשים מותרים מופרדים בפסיקים. ניתן להשתמש: 1234567890*# 
 times אופציונלי מספר כמה פעמים לחזור על התפריט לפני שמחזיר שגיאה. ברירת מחדל 1 , מקסימום 9 (ערך גבוה יותר נחתך ל-9) 
 timeout אופציונלי שניות כמה שניות לחכות להקשה לפני חזרה 
 errorReturn אופציונלי "ERROR" הערך שיוחזר אם פג הזמן ללא הקשה 
 extensionChange אופציונלי ID / "." / ".." לאן לעבור אחרי מיצוי times :
 "." = חזרה לשלוחה הנוכחית
 ".." = חזרה לשלוחה קודמת
מספר = ID שלוחה ספציפית 
 setMusic אופציונלי "yes" / "no" מוזיקת המתנה בזמן שהשרת מעבד 
 maskLog אופציונלי true מסתיר בלוג את ההקשה שנבחרה (ערך ממוסך). ראו getDTMF . 
 files אופציונלי מערך קבצי שמע להשמעה לפני ההמתנה 
 דוגמה:
 {
 "type" : "simpleMenu" ,
 "name" : "menuChoice" ,
 "times" : 3 , // חזור עד 3 פעמים 
 "timeout" : 5 , // המתן 5 שניות להקשה 
 "enabledKeys" : "1,2,3" , // רק מקשים 1, 2, 3 
 "setMusic" : "no" ,
 "files" : [
 { "text" : "הקישו 1 למכירות, 2 לתמיכה, 3 לחיוב" }
 ]
}
 מה יחזור לשרת שלכם:
 ...& menuChoice=1 
 אם פג הזמן: ...& menuChoice=ERROR 
 קבלת הקשות
 type: "getDTMF" 
 מאפשר לקבל קלט מספרי חופשי מהמתקשר — מספר תעודת זהות, קוד לקוח, טלפון וכו'.
 בניגוד לתפריט פשוט, כאן ניתן לקבל מספר ספרות ברצף.
 פרמטר חובה? ערכים הסבר 
 type חובה "getDTMF" סוג המודול 
 name חובה שם כלשהו שם הפרמטר שיחזור עם הקלט 
 max חובה מספר מקסימום ספרות לקבל 
 min אופציונלי מספר מינימום ספרות — אם הוקשו פחות, יבקש שוב 
 timeout אופציונלי שניות זמן המתנה בין ספרה לספרה 
 skipKey אופציונלי מקש (כגון "#") מקש שמסיים קלט מוקדם, ללא צורך להגיע ל-max 
 skipValue אופציונלי טקסט הערך שיישלח אם הוקש מקש הדילוג ללא קלט קודם 
 confirmType אופציונלי 
 number מקריא כמספר שלם (ברירת מחדל)
 digits מקריא ספרה-ספרה
 no ללא קריאה חוזרת
 setMusic אופציונלי "yes" / "no" מוזיקת המתנה בזמן עיבוד בשרת 
 maskLog אופציונלי true מסתיר בלוג ה-API ( ivrApiLog ) את הקלט שהוקש — נשמר ערך ממוסך : 2 תווים ראשונים + 2 אחרונים והשאר XXXX (קלט קצר של עד 4 תווים — התו הראשון בלבד). הקלט המלא נשלח לשרת שלכם כרגיל; רק העותק שנשמר בלוג ממוסך. לנתונים רגישים כמו פרטי אשראי / ת.ז. 
 post אופציונלי true שולח את הקריאה החוזרת (ואילך) ב- POST במקום GET — הקלט עובר לגוף הבקשה ולא ל-URL. דביק עד סוף השיחה. ראו שיטת שליחה . 
 files אופציונלי מערך הודעה לפני קבלת הקלט 
 נתונים רגישים בלוג: כשמבקשים מהמתקשר פרטי אשראי, CVV, ת.ז. וכד' — הוסיפו "maskLog": true לאלמנט. הקלט המלא עדיין נשלח לשרת שלכם, אך בלוג ה-API יישמר רק ערך ממוסך — למשל כרטיס 1234567890123456 יירשם 12XXXX56 ו-CVV 123 יירשם 1XXXX . כך נתונים רגישים לא נשמרים בלוג. חל על כל מודולי הקלט ( getDTMF , simpleMenu , record , stt ).
 דוגמה — בקשת תעודת זהות:
 {
 "type" : "getDTMF" ,
 "name" : "idNumber" ,
 "max" : 9 , // ת.ז. — 9 ספרות 
 "min" : 5 , // לפחות 5 ספרות 
 "timeout" : 5 ,
 "skipKey" : "#" , // # מסיים קלט מוקדם 
 "skipValue" : "SKIP" , // אם הקיש # ריק 
 "confirmType" : "digits" ,
 "files" : [
 { "text" : "אנא הזינו את מספר תעודת הזהות שלכם" }
 ]
}
 מה יחזור:
 ...& idNumber=123456789 
 אם הקיש # ריק: ...& idNumber=SKIP 
 דוגמה — כרטיס אשראי עם הסתרה בלוג:
 {
 "type" : "getDTMF" ,
 "name" : "cardNumber" ,
 "max" : 16 ,
 "confirmType" : "no" ,
 "maskLog" : true , // יישמר בלוג ממוסך; לשרת נשלח מלא 
 "files" : [
 { "text" : "אנא הקישו את 16 ספרות כרטיס האשראי" }
 ]
}
 מה יחזור לשרת שלכם:
 ...& cardNumber=1234567890123456 (מלא) 
 מה יישמר בלוג:
 ...& cardNumber=12XXXX56 (ממוסך) 
 קבלת הקלטות
 type: "record" 
 מקליט הודעה קולית מהמתקשר ושומר אותה כקובץ שמע במערכת.
 מתאים להשארת הודעה, איסוף חוות דעת, ועוד.
 פרמטר חובה? ערכים הסבר 
 type חובה "record" סוג המודול 
 name חובה שם בסיס לשמות הפרמטרים שיחזרו (ראו תגובה למטה) 
 max אופציונלי שניות אורך מקסימלי להקלטה 
 min אופציונלי שניות אורך מינימלי להקלטה 
 confirm אופציונלי 
 confirmOnly בקש אישור + אפשרות שמיעה ב-2 (ברירת מחדל)
 ful השמע ובקש אישור
 no ללא אישור
 fileName אופציונלי שם קובץ שם הקובץ לשמירה במערכת 
 saveFolder אופציונלי ID שלוחה לשמור לתיקיית שלוחה אחרת (לא ברירת המחדל) 
 hangupSave אופציונלי "yes" / "no" מה לעשות כשהמתקשר מנתק באמצע ההקלטה .
 "yes" = ההקלטה נשמרת רגיל, בכל אורך, בדיוק כמו הקלטה שאושרה.
ברירת מחדל "no" = ההקלטה נשמרת לסל המחזור, ורק אם ארכה 4 שניות ומעלה — קצרה מזה לא נשמרת כלל 
 sttSoft אופציונלי true תמלול "רך" ברקע: ניסיון תמלול חד-פעמי בלי לכפות — לא משמיע לאישור ולא מבקש להקליט שוב. הקובץ נשמר כרגיל והטקסט (אם הצליח) חוזר ב- TEXT_<name> . מקבל גם את הטיות התמלול של stt ( sttMode / sttCities / sttPhrases …) 
 maskLog אופציונלי true מסתיר בלוג את ערכי הקלט של ההקלטה (כולל טקסט TEXT_ אם קיים). ראו getDTMF . 
 files אופציונלי מערך הודעה להשמעה לפני ההקלטה 
 הקלטה + תמלול ברקע: רוצים הקלטה רגילה אבל גם טקסט מתומלל "כבונוס"? הוסיפו "sttSoft": true . בניגוד ל- stt שכופה תמלול (משמיע לאישור + מבקש להקליט שוב אם נכשל), כאן חוויית המתקשר זהה להקלטה רגילה — והטקסט חוזר בנפרד ב- TEXT_<name> (ריק אם התמלול נכשל). חיוב תמלול רק בהצלחה.
 דוגמה:
 {
 "type" : "record" ,
 "name" : "userMessage" ,
 "max" : 30 ,
 "min" : 2 ,
 "confirm" : "confirmOnly" ,
 "fileName" : "msg_{{PBXphone}}" ,
 "files" : [
 { "text" : "אנא השאירו הודעה לאחר הצליל" }
 ]
}
 דוגמה — הקלטה עם תמלול רך ברקע:
 {
 "type" : "record" ,
 "name" : "msg" ,
 "sttSoft" : true ,
 "confirm" : "no" ,
 "files" : [
 { "text" : "אנא השאירו הודעה לאחר הצליל" }
 ]
}
 מה יחזור — פרמטרים מרובים:
 userMessage = שם הקובץ שנוצר
 FILE_userMessage = שם הקובץ
 FILEID_userMessage = מזהה הקובץ במערכת
 PATH_userMessage = נתיב מלא לקובץ
 SIZE_userMessage = גודל ב-MB
 DURATION_userMessage = משך בשניות
 DIGIT_userMessage = המקש בו אושרה ההקלטה
 TEXT_userMessage = הטקסט המתומלל — רק כש- sttSoft:true (ריק אם התמלול נכשל)
 למשוך את קובץ השמע לשרת שלכם: ה- FILEID_<name> הוא המפתח להורדה או להשמעה בדפדפן:
 GET ivrFilesApi.php?action=fileDownload&audio= {FILEID} &apiKey=... // הורדה כקובץ 
GET ivrFilesApi.php?action=fileDownload&audio= {FILEID} &play=1&apiKey=... // השמעה ישירה ב-<audio> 
 הקובץ מוגש תמיד כ-MP3. תיעוד מלא: fileDownload .
 המתקשר ניתק באמצע ההקלטה: ההקלטה עדיין נשמרת, ואותה חבילת פרמטרים בדיוק נשלחת אליכם — כולל FILEID_<name> , כך שאפשר למשוך את האודיו בדיוק כמו בהקלטה שאושרה.
 ההבדל היחיד: DIGIT_<name> יחזור ריק, כי לא הוקש מקש אישור.
 מומלץ להוסיף "hangupSave": "yes" — בלעדיו ההקלטה נכנסת לסל המחזור, והקלטות קצרות מ-4 שניות לא נשמרות בכלל.
 תמלול קולי (Speech-to-Text)
 type: "stt" 
 מקליט את המתקשר ו ממיר את הקול לטקסט .
 המתקשר מדבר — אתם מקבלים מחרוזת טקסט מוכנה לעיבוד.
 עלות: 0.25 יחידות לכל 10 שניות. מקסימום הקלטה: 10 שניות. 
 פרמטר חובה? הסבר 
 type חובה "stt" 
 name חובה שם הפרמטר שיחזור עם הטקסט המתומלל 
 max אופציונלי מקסימום שניות (עד 10) 
 min אופציונלי מינימום שניות 
 fileName אופציונלי שם הקובץ לשמירה 
 saveFolder אופציונלי ID שלוחה לשמירת קובץ הקול 
 campaignBilling אופציונלי מזהה קמפיין לשיוך לחיוב 
 maskLog אופציונלי מסתיר בלוג את הטקסט המתומלל (ערך ממוסך). ראו getDTMF . 
 files אופציונלי הודעה לפני ההקלטה 
 דוגמה:
 {
 "type" : "stt" ,
 "name" : "spokenText" ,
 "max" : 8 ,
 "min" : 1 ,
 "files" : [
 { "text" : "אנא אמרו את שמכם לאחר הצליל" }
 ]
}
 מה יחזור:
 spokenText = הטקסט שתומלל (לדוג': "יוסי כהן")
 FILE_spokenText = שם קובץ הקול
 FILEID_spokenText = מזהה הקובץ במערכת
 PATH_spokenText = נתיב מלא לקובץ
 SIZE_spokenText = גודל ב-MB
 DURATION_spokenText = משך בשניות
 DIGIT_spokenText = מקש האישור
 גם כאן FILEID_<name> מאפשר למשוך את קובץ הקול ב- ivrFilesApi.php?action=fileDownload&audio={FILEID}&apiKey=... , וגם כשהמתקשר מנתק באמצע. ראו את ההערות במודול קבלת הקלטות , כולל hangupSave .
 ניתוב שיחה בסיסי
 type: "simpleRouting" 
 מעביר את השיחה לטלפון ישראלי — נייד או נייח.
 מתאים לניתוב לנציג, לנייד של עובד, וכדומה.
 חובה: dialPhone חייב להיות מספר טלפון ישראלי תקין (נייד/נייח).
 פרמטר חובה? הסבר 
 type חובה "simpleRouting" 
 name חובה שם הפרמטר שיחזיר סטטוס ביצוע השיחה 
 dialPhone חובה מספר הטלפון לחיוג (ישראלי בלבד) 
 displayNumber אופציונלי המספר שיוצג אצל המקבל. ריק = מספר המתקשר המקורי 
 addDigits אופציונלי ספרות שיצורפו לסוף מספר המתקשר לצורך זיהוי 
 routingMusic אופציונלי "yes" = מוזיקת המתנה | "no" = צליל חיוג רגיל 
 ringSec אופציונלי שניות צלצול לפני ניתוק 
 limit אופציונלי הגבלת משך השיחה בשניות 
 endCall אופציונלי "yes" / "no" — מה קורה כשהצד המחוייג מנתק אחרי שהשיחה נענתה.
 "yes" (ברירת מחדל) = גם המתקשר מנותק והשיחה נגמרת.
 "no" = המתקשר נשאר על הקו והזרימה ממשיכה לפעולה הבאה 
 cancelKey אופציונלי "yes" = מקש ביטול : המתקשר מקיש * בזמן שהיעד מצלצל ← החיוג מבוטל, המתקשר נשאר על הקו והזרימה חוזרת לשרת שלכם עם CANCEL ו- CANCELKEY_<name>=yes . ברירת מחדל: ללא מקש ביטול 
 midCallType אופציונלי צירוף ערוץ במקש באמצע השיחה : extension (שלוחה), phone (טלפון) או api (לינק לסקריפט). ברירת מחדל: ללא צירוף. ראו הסבר למטה 
 midCallTarget אופציונלי מה מצטרף: מזהה או נתיב שלוחה, מספר טלפון, או כתובת הסקריפט. חובה יחד עם midCallType 
 midCallKey אופציונלי המקש שפותח וסוגר את הערוץ: * , # , או *1 עד *9 . ברירת מחדל: * . יחד עם cancelKey מקש שמתחיל בכוכבית מוחלף ב- # 
 midCallSide אופציונלי איפה נמצא הנציג, שרק הוא יכול ללחוץ על המקש: caller (המתקשר), callee (מי שעונה) או auto (ברירת מחדל: בשיחה שיצאה משלוחת SIP הנציג הוא המתקשר, ובכל שיחה אחרת הוא מי שעונה) 
 midCallCid אופציונלי הזיהוי שיוצג לטלפון שמצטרף (מספר מאושר של המערכת). ברירת מחדל: מספר הלקוח 
 campaignBilling אופציונלי מזהה קמפיין לשיוך לחיוב 
 recordSplit אופציונלי "yes" = הקלטה נפרדת לכל צד : מלבד ההקלטה המשותפת נשמרים גם קובץ של המתקשר בלבד וקובץ של הנציג בלבד. ברירת מחדל: הקלטה משותפת בלבד. ראו הקלטה נפרדת לכל צד 
 eventsUrl אופציונלי כתובת webhook לשיחה הזו בלבד : אירועי המתנה/מענה/ניתוק, וסיום השיחה ( completed , אחרי שההקלטות עלו), נשלחים לכתובת הזו במקום לכתובת שהוגדרה למערכת. הכתובת חלה עד סוף השיחה, גם על ניתובים נוספים בה. http:// או https:// בלבד. תוכן ההודעות, החתימה והניסיונות החוזרים: תיעוד ה-API , אירועי שיחה. 
 צירוף ערוץ במקש באמצע השיחה: עם "midCallType" ו- "midCallTarget" הנציג יכול ללחוץ על המקש בזמן השיחה, ושלוחה, טלפון או סקריפט מצטרפים אליה. הנציג והלקוח ממשיכים לשמוע ולדבר, ולחיצה נוספת סוגרת רק את הערוץ שצורף. ניתוק של הנציג או של הלקוח מסיים את כל השיחה.
 סקריפט שצורף מקבל PBXcallType=midcall , את טלפון הלקוח ב- PBXphone ואת מזהה השיחה המקורית ב- PBXmidCallParent . טלפון שצורף מחויב כשיחה יוצאת רגילה.
 שימו לב: הנציג שומע את מה שהלקוח אומר וייתכן שגם את צלילי ההקשות שלו, ושיחה מוקלטת ממשיכה להיות מוקלטת. קחו זאת בחשבון לפני שמבקשים פרטים רגישים.
 מקש ביטול בזמן החיוג: עם "cancelKey": "yes" המתקשר יכול להקיש * בזמן שהיעד מצלצל. החיוג ליעד מבוטל, המתקשר נשאר על הקו, ואתם מקבלים CANCEL יחד עם CANCELKEY_<name>=yes (להבדיל מ- CANCEL רגיל, שבו המתקשר עצמו ניתק). כך אפשר להציע לו יעד אחר, לחזור לתפריט וכו'.
 המקש הוא * בלבד (מקובע במרכזיה). הקשת * אחרי שהיעד ענה מנתקת את היעד ומחזירה את המתקשר לזרימה עם ANSWER — בשילוב "endCall": "no" המתקשר יכול לסיים שיחה ולעבור ליעד הבא; בלי endCall השיחה מסתיימת כרגיל. ה- * עצמו אינו מועבר ליעד.
 הקלטה נפרדת לכל צד (לתמלול וניתוח שיחות): בשיחה מוקלטת רגילה שני הצדדים נשמעים באותו קובץ. עם הקלטה נפרדת נשמרים בכל שיחה שנענתה שלושה קבצים: ההקלטה המשותפת (בדיוק כמו היום — מייל, השמעה ושמירה בשלוחה ממשיכים כרגיל), קובץ של המתקשר בלבד וקובץ של הנציג בלבד. שלושת הקבצים מתחילים באותו רגע, כך שאפשר ליישר ביניהם לפי זמן.
 מי זה מי: המתקשר ( caller ) הוא תמיד הלקוח, והנציג ( agent ) הוא תמיד הצד שלכם. בשיחה נכנסת שנותבה — המתקשר הוא מי שהתקשר, והנציג הוא מי שענה. בשיחה יוצאת משלוחת SIP — המתקשר הוא הצד החיצוני שענה, והנציג הוא השלוחה שחייגה.
 הפעלה (כבוי כברירת מחדל):
 ניתוב מתגובת ה-API: "recordSplit": "yes" בפעולה simpleRouting , ipRouting או queueRouting .
 שלוחת ניתוב שיחה או שלוחת נתב שיחות: בהגדרות השלוחה, "הקלטה נפרדת לכל צד".
 שיחות יוצאות משלוחות SIP: בהגדרות המערכת, "הקלטה נפרדת לכל צד גם בשיחות יוצאות". אפשר גם לקבוע לכל שלוחה בנפרד (פעיל / כבוי / לפי הגדרות המערכת) בעריכת השלוחה, או ב- recordSplit של sipCreate / sipUpdate . הגדרת השלוחה גוברת על הגדרת המערכת.
 שליפת הקבצים: ivrFilesApi.php?action=outboundCalls ו- action=callHistory . בכל פריט ב- recordings שיש לו הקלטה נפרדת מופיעים, מלבד recUrl (המשותפת), גם callerRecUrl ו- agentRecUrl . בלי הקלטה נפרדת השדות לא מופיעים.
 שימו לב: הקבצים הנפרדים מוכנים כמה שניות אחרי סוף השיחה. שיחה שלא נענתה, תא קולי והעברה ישירה בלי הקלטה לא יוצרים קבצים נפרדים. הקבצים בפורמט opus, מונו, 8 קילוהרץ (איכות הקו הטלפוני). כל שיחה תופסת בערך פי שלושה נפח אחסון. אם צורף לשיחה ערוץ שלישי ( midCallType ), הוא נשמע בקובץ של המתקשר. ההגדרה חלה על שיחות מרגע ההפעלה ואילך.
 הקלטה: כל ניתוב שנענה מוקלט אוטומטית — אין פרמטר להקלטה ואין צורך ב- queueRouting או במעבר לשלוחה. ההקלטה נשלפת ב- ivrFilesApi.php?action=outboundCalls&callId=<PBXcallId> (שדה recordings[].recUrl ), גם כשהניתוב בוצע מתוך שיחת קמפיין ( campaignRun עם messagesType=apiUrl ). שמרו את PBXcallId בזמן השיחה ושלפו אחרי קריאת ה- HANGUP .
 להמשיך את השיחה אחרי הניתוב: כברירת מחדל, שיחה שנענתה ואז הצד המחוייג ניתק — מסיימת גם את השיחה עם המתקשר. עם "endCall": "no" המתקשר נשאר על הקו, אתם מקבלים את הסטטוס ( ANSWER + משך השיחה), ויכולים להמשיך — להשמיע הודעה, להציע לדבר עם נציג אחר, לבקש דירוג וכו'.
 באין-מענה / תפוס / שגיאה הזרימה ממשיכה תמיד, ללא קשר ל- endCall .
 שימו לב: אם המתקשר עצמו מנתק — השיחה נגמרת בכל מקרה. אין פרמטר שמונע זאת.

 פרטי השיחה בכותרות SIP
 בכל שיחה שמנותבת ליעד IP נוספות ל-INVITE כותרות עם פרטי השיחה — באותם שמות כמו
 הפרמטרים שנשלחים לשרת ה-API, בתוספת X- . כך המרכזייה שלכם יודעת, למשל,
 לאיזה מספר חייגו (כולל מספר משני של המערכת) — ולא רק מי המתקשר.
 זה פועל גם בשלוחת ניתוב IP שהוגדרה בממשק, וגם בניתוב שמגיע מתגובת API.
 כותרת תוכן 
 X-PBXdid המספר שאליו חייגו (גם מספר משני) 
 X-PBXphone מספר המתקשר 
 X-PBXnum המספר הראשי של המערכת 
 X-PBXcallId מזהה השיחה — זהה ל- PBXcallId שמגיע ב-API 
 X-PBXcallType סוג השיחה — כמו PBXcallType 
 X-PBXextensionId מזהה השלוחה — כמו PBXextensionId 
 X-PBXdiversion מפנה השיחה — רק כשהשיחה הגיעה מופנית (ראו שיחה מופנית ) 
 קריאת הכותרת באסטריסק:
 ; chan_sip 
same => n,Set(DIALED=${SIP_HEADER(X-PBXdid)})
 ; PJSIP 
same => n,Set(DIALED=${PJSIP_HEADER(read,X-PBXdid)})
 ניתוב לתור / Router
 type: "queueRouting" 
 מנתב את השיחה לתור חיוג לנציגים. יש שתי דרכים להפעיל — אפשר לבחור ביניהן בכל שיחה:
 א. נתב שמור (קיים): מעבירים routerId בלבד, וכל הגדרות הניתוב (נציגים, זמני המתנה, פעולות סגירה/אי-מענה) נלקחות מהנתב שהוגדר מראש בממשק הניהול.
 ב. בלוק מלא בזמן אמת (חדש): שולחים את הגדרות הניתוב (אובייקט router ) ואת רשימת הטלפונים לחיוג ( phones ) ישירות בתגובה — בלי להגדיר נתב מראש. מתאים כשהאפליקציה שלכם מחליטה בזמן אמת למי לחייג (למשל: הנציגים הזמינים כרגע לפי הלוגיקה שלכם). אין צורך בכללי שעות/ימים על הטלפונים — אתם שולחים את היעדים הרלוונטיים לאותו רגע.
 הדרך הקיימת לא השתנתה. אם נשלח routerId — משתמשים בנתב השמור. אחרת, אם נשלחו router / phones — מצב הבלוק.
 מוזיקה בהמתנה: אפשר לקבוע מוזיקה לכל תור. סדר העדיפויות: הפרמטר music בקריאה, המוזיקה שהוגדרה לנתב (בממשק הניהול, בעריכת הנתב, או router.music בדרך ב'), ואז המוזיקה הפעילה של המערכת. את הערכים מקבלים מ- העלאה ורשימה של מוזיקה בהמתנה .

 "type" : "queueRouting" ,
 "routerId" : "42" ,
 "music" : "IP_MUSIC_2" 
}
 המשך השיחה בלי נציגים או בלי מענה: 
 {
 "type" : "queueRouting" ,
 "routerId" : "42" ,
 "name" : "queueResult" ,
 "continueOnFail" : "yes" 
}
 מה יחזור לשרת שלכם:
 queueResult = NOAGENTS (אין נציגים זמינים), NOANSWER (אף נציג לא ענה עד תום ההמתנה) או ERROR 
 STEXT_queueResult = תיאור התוצאה. ב- ERROR : NO_BALANCE או ROUTER_NOT_FOUND 
 RINGL_queueResult = משך ההמתנה בתור בשניות
 ANSWERL_queueResult = תמיד 0 
 עם continueOnFail לא מושמעות הודעות אין מענה או סגור של הנתב, ולא מופעלות failingAction ו- closeAction . המתקשר שומע רק את מה שתחזירו. שיחה שנענתה מסתיימת כרגיל ולא חוזרת לשרת.

 נגן מדיה
 type: "audioPlayer" 
 מנגן קבצי שמע בסדר רצוף ומחזיר מידע מפורט על ההאזנה — כמה האזין, איפה עצר, באיזה קובץ.
 מתאים לניגון תוכן ארוך, שיעורים, פרקי פודקאסט.
 המשך האזנה: לא אוטומטי ב-API.
 שמרו את POSITION_name שחזר, ושלחו אותו ב- startSecond (במילישניות) בפנייה הבאה כדי להמשיך מהמקום שנעצר.
 ערכים חוזרים (name = השם שנתתם למודול), בסיום ההאזנה ובקריאת PBXcallStatus=HANGUP אם נותקו באמצע:
 name = end (יציאה במקש) / finished (הושמע עד הסוף) / hangup ·
 FILE_name מזהה הקובץ שבו נעצרה ההאזנה ·
 POSITION_name המיקום בשניות ·
 DURATION_name סך שניות ההאזנה ·
 LISTENED_name JSON של שניות האזנה לכל קובץ.
 פרמטר חובה? ערכים הסבר 
 type חובה "audioPlayer" סוג המודול 
 name חובה שם כלשהו שם הפרמטר לתוצאה 
 files חובה מערך הקבצים לניגון — ראו מקטע "קבצי שמע" 
 startFile אופציונלי מספר (מ-1) מאיזה קובץ במערך להתחיל 
 startSecond אופציונלי מילי-שניות מאיזה רגע בקובץ להתחיל (1000 = שניה) 
 beepPlay אופציונלי YES / NO ביפ בין קבצים (ברירת מחדל: YES) 
 playLength אופציונלי YES / NO השמעת אורך הקובץ (ברירת מחדל: NO) 
 digitsSource אופציונלי "template" / אחר מקור הגדרת מקשים אינטראקטיביים 
 playTemplate אופציונלי מזהה תבנית בשימוש עם digitsSource: "template" 
 keyActions אופציונלי אובייקט מקש→פעולה מיפוי מקשים מלא לניגון — ראו טבלת ערכי המקשים למטה 
 apiUrls אופציונלי אובייקט מקש→URL למקשים שהוגדרו "apiCall" — כתובת ה-API שתיקרא בלחיצה. ראו מקש API ופעולת playerControl 
 apiAfters אופציונלי אובייקט מקש→ערך למקשי apiCall — מה קורה בסיום הקריאה כשלא הוחזרה פעולת נגן: resume (ברירת מחדל) / restart / next / exit 
 ערכי מקשים (keyActions):
 כל מקש ( 0 – 9 , STAR , POUND ) יכול לקבל אחת מהפעולות:
 end (יציאה) · next (קובץ הבא) · back (קובץ קודם) ·
 secondsForward / secondsBack (דילוג בשניות) ·
 minutesForward / minutesBack (דילוג בדקות) ·
 break (השהיה/המשך) · pause (השהיה עד מקש) ·
 speedUp / speedDown (מהירות) · volumeUp / volumeDown (עוצמה) ·
 lastPositions (חזרה למיקום קודם) · manage (ניהול הקובץ) ·
 none (לא פעיל) · apiCall (קריאה ל-API — חדש) .
 מקש חכם — apiCall : בלחיצה על המקש המרכזיה קוראת לכתובת שהוגדרה לו
 (ב- apiUrls או בהגדרות השלוחה בממשק), עם מיקום ההאזנה המדויק והקובץ הנוכחי.
 השרת שלכם יכול להשמיע הודעה/טקסט, להקליט, לגבות, להעביר שלוחה — כל פעולות המדריך הזה —
 וגם להחזיר playerControl כדי לשלוט בניגון עצמו
 (דילוג, קפיצה למיקום, קובץ הבא, מהירות, יציאה). פירוט מלא בהמשך.
 דוגמה — המשך האזנה מנקודת עצירה:
 {
 "type" : "audioPlayer" ,
 "name" : "listenResult" ,
 "startFile" : 1 , // התחל מקובץ ראשון 
 "startSecond" : 45000 , // המשך מ-45 שניות 
 "beepPlay" : "NO" ,
 "files" : [
 { "fileId" : "1001" },
 { "fileId" : "1002" }
 ]
}
 דוגמה — נגן עם מקש API חכם:
 {
 "type" : "audioPlayer" ,
 "name" : "listenResult" ,
 "files" : [ { "fileId" : "1001" } ],
 "keyActions" : { "1" : "secondsBack" , "3" : "secondsForward" , "5" : "apiCall" , "0" : "end" },
 "apiUrls" : { "5" : "https://your-server.com/player-key" },
 "apiAfters" : { "5" : "resume" } // בסיום ה-API — המשך מאותו מיקום 
}
 שליטה בנגן — מקש API
 type: "playerControl" 
 בנגן המדיה (הודעות מערכת / נגן קבצים) ניתן להגדיר לכל מקש את הפעולה apiCall —
 "קריאה ל-API". בלחיצה על המקש, באמצע ההשמעה, המרכזיה קוראת לכתובת שהוגדרה למקש
 ומבצעת את פעולות ה-JSON שיוחזרו — בדיוק כמו כל מודול API (השמעת קובץ/טקסט,
 תפריט, הקלטה, גבייה, מעבר לשלוחה…). בנוסף, התשובה יכולה לכלול פעולת
 playerControl — הנחיה לנגן עצמו מה לעשות כשהשליטה חוזרת אליו.
 מה נשלח לשרת שלכם בלחיצת המקש:
 כל הפרמטרים הקבועים הרגילים, ובנוסף פרמטרי ההקשר של הנגן:
 פרמטר הסבר 
 event תמיד playerKey — מזהה שהקריאה הגיעה ממקש בנגן 
 playerKey המקש שנלחץ ( 0 – 9 , STAR , POUND ) 
 playerFileId מזהה הקובץ שהושמע 
 playerFileName שם המערכת של הקובץ 
 playerFileTitle השם התצוגתי של הקובץ 
 playerPosition המיקום בקובץ ברגע הלחיצה, בשניות (למשל 73.4 ) 
 playerFileIndex מספר הקובץ הנוכחי ברצף (מ-1) 
 playerFilesCount סך הקבצים ברצף 
 פעולת playerControl בתשובה:
 פרמטר חובה? ערכים הסבר 
 type חובה "playerControl" סוג הפעולה 
 action חובה ראו טבלה למטה מה הנגן יעשה כשהשליטה תחזור אליו 
 seconds אופציונלי מספר כמות השניות ל- secondsForward / secondsBack (ברירת מחדל: 10) 
 minutes אופציונלי מספר כמות הדקות ל- minutesForward / minutesBack (ברירת מחדל: 10) 
 position אופציונלי שניות מיקום מוחלט ל- action: "position" — למשל 95.5 
 ערכי action:
 ערך הסבר 
 resume המשך ההשמעה מאותו מיקום (זו גם ברירת המחדל כשאין playerControl בתשובה) 
 restart השמעת הקובץ הנוכחי מההתחלה 
 position קפיצה למיקום מוחלט בקובץ — לפי position (בשניות) 
 secondsForward / secondsBack דילוג קדימה/אחורה — לפי seconds 
 minutesForward / minutesBack דילוג קדימה/אחורה — לפי minutes 
 next / back מעבר לקובץ הבא / הקודם ברצף 
 speedUp / speedDown שינוי מהירות ההשמעה בדרגה אחת 
 volumeUp / volumeDown שינוי עוצמת ההשמעה בדרגה אחת 
 lastPositions תפריט חזרה למיקום קודם בקובץ 
 end / exit יציאה מהנגן (המשך לשלוחה הבאה לפי הגדרות השלוחה) 
 דוגמה — השמעת הודעה ואז קפיצה למיקום:
 המאזין לחץ על המקש בדקה 1:13; השרת מחזיר הודעה קולית ומזיז את ההאזנה לדקה 5:00:
 [
 { "type" : "simpleMessage" , "files" : [ { "text" : "מדלג לפרק הבא" } ] },
 { "type" : "playerControl" , "action" : "position" , "position" : 300 }
]
 דוגמה — סימניה (bookmark) בשרת שלכם:
 שומרים את playerPosition אצלכם, ומחזירים אישור קולי בלבד — ההשמעה ממשיכה מאותו מיקום:
 [
 { "type" : "simpleMessage" , "files" : [ { "text" : "הסימניה נשמרה" } ] },
 { "type" : "playerControl" , "action" : "resume" }
]
 דוגמה — איסוף קלט באמצע האזנה (זרימה דו-שלבית):
 אפשר לשלב כל מודול לפני ההנחיה לנגן — למשל שאלון קצר. שימו לב:
 playerControl מסיים את שיחת ה-API , לכן קודם אוספים
 את הקלט (בלי playerControl), מקבלים אותו בקריאה החוזרת, ורק אז מחזירים את ההנחיה לנגן:
 תשובה 1 — איסוף בלבד:
 [
 { "type" : "getDTMF" , "name" : "rating" , "max" : 1 ,
 "files" : [ { "text" : "דרגו את השיעור מ-1 עד 5" } ] }
]
 קריאה חוזרת אליכם — עם rating=4 וכל פרמטרי ההקשר. תשובה 2 — סיום והמשך האזנה:
 [
 { "type" : "simpleMessage" , "files" : [ { "text" : "תודה על הדירוג" } ] },
 { "type" : "playerControl" , "action" : "resume" }
]
 כללי התנהגות: 
 ללא playerControl בתשובה — הנגן פועל לפי הגדרת "בסיום פעולת ה-API" של המקש ( resume / restart / next / exit ; ברירת מחדל: המשך מאותו מיקום).
 אם התשובה העבירה את השיחה לשלוחה אחרת ( goTo / extensionChange / switchSystem ) — ההשמעה לא תחודש.
 playerControl מבוצע אחרי שכל שאר הפעולות באותה תשובה הסתיימו (קודם ההודעה, אחר-כך הדילוג), ומסיים את שיחת ה-API — ערכי קלט שנאספו באותה תשובה לא יישלחו חזרה. לאיסוף קלט: קודם המודול לבד, ובקריאה החוזרת מחזירים playerControl .
 מחוץ להקשר של מקש-נגן, פעולת playerControl לא עושה דבר.
 מעבר לשלוחה אחרת
 type: "goTo" 
 מעביר את השיחה לשלוחה אחרת במרכזיה.
 שימושי לניתוב דינמי על פי לוגיקה עסקית — שעות פעילות, סוג לקוח, זמינות נציגים וכו'.
 בחירת היעד נעשית באחד מארבעה פרמטרים (לפי סדר עדיפות) — לפי נתיב או לפי מזהה (ID) :
 פרמטר חובה? הסבר 
 type חובה "goTo" (או "extensionChange" — זהה) 
 goTo אחד מהארבעה נתיב השלוחה (path) — מתורגם דרך מנגנון הנתיבים 
 extensionPathChange אחד מהארבעה נתיב השלוחה (path) — זהה ל- goTo , עדיפות גבוהה יותר 
 extensionIdChange אחד מהארבעה מזהה השלוחה המדויק (ID), ללא תרגום נתיב 
 extensionChange אחד מהארבעה מזהה השלוחה המדויק (ID) — ברירת המחדל אם לא נשלח אחר 
 {
 "type" : "goTo" ,
 "goTo" : "1/3" // נתיב השלוחה 
}
 מעבר למערכת אחרת
 type: "switchSystem" 
 מעביר את השיחה למערכת (חשבון מרכזיה) אחרת לגמרי, ולא רק לשלוחה אחרת באותה מערכת.
 השיחה נכנסת למערכת היעד עם נתיב התחלה אופציונלי, והמערכת המקורית נשמרת ב"מחסנית מעבר"
 כדי שאפשר יהיה לחזור אליה בהמשך עם switchReturn .
 תנאים לביצוע המעבר: 
 (1) הזוג מקור→יעד חייב להיות מאושר מראש בטבלת ivr_system_switch_allowed ;
 (2) targetNum חייב להיות שונה מהמערכת הנוכחית ולהיות מערכת קיימת;
 (3) עומק המעבר המרבי הוא 5 (לא ניתן לשרשר יותר מ-5 מעברים פתוחים).
 אם תנאי לא מתקיים — המעבר לא מתבצע והשיחה ממשיכה כרגיל.
 פרמטר חובה? הסבר 
 type חובה "switchSystem" 
 targetNum חובה מספר המערכת (החשבון) שאליה לעבור 
 targetPath אופציונלי נתיב השלוחה במערכת היעד שבה להתחיל 
 {
 "type" : "switchSystem" ,
 "targetNum" : "2005" ,
 "targetPath" : "1/3" 
}
 חזרה ממערכת (switchReturn)
 type: "switchReturn" 
 מחזיר את השיחה למערכת המקורית שממנה הגיעה דרך switchSystem —
 שולף את המסגרת האחרונה ממחסנית המעבר וממשיך שם.
 אם השיחה לא הגיעה ממעבר (המחסנית ריקה), ההתנהגות נקבעת לפי noSourceAction .
 פרמטר חובה? הסבר 
 type חובה "switchReturn" 
 returnPath אופציונלי נתיב שאליו לחזור במערכת המקור 
 noSourceAction אופציונלי מה לעשות כשאין מערכת מקור במחסנית: hangup (ברירת מחדל) או goToPath 
 goToPath אופציונלי נתיב לקפיצה כש- noSourceAction = goToPath 
 {
 "type" : "switchReturn" ,
 "noSourceAction" : "hangup" 
}
 החלפת לינק
 type: "changeUrl" 
 מחליף את כתובת ה-API שאליה המרכזיה פונה בהמשך השיחה — בלי לעבור שלוחה.
 שימושי למעבר בין שלבים/שרתים תוך כדי אותו תהליך.
 אם הלינק החדש כולל פרמטרים ( ?a=1&b=2 ) — הם הופכים לפרמטרים הקבועים של הכתובת.
 פרמטר חובה? ערך הסבר 
 type חובה "changeUrl" סוג המודול (גם "changeLink" ) 
 url רשות כתובת מלאה הלינק החדש. אם לא צוין — נשארים על אותו לינק 
 clearRequest רשות "yes" / "no" האם לנקות את ערכי ה-REQUEST שנצברו.
 ברירת מחדל: "yes" (ניקוי). הפרמטרים הקבועים ( addParams ) תמיד נשמרים 
 {
 "type" : "changeUrl" ,
 "url" : "https://my.server/api?env=prod" ,
 "clearRequest" : "yes" // ניקוי הערכים שנצברו (ברירת מחדל) 
}
 אחרי changeUrl המרכזיה פונה מיד ללינק החדש לפנייה נוספת —
 ניתן לשלב יחד addParams / removeParams 
 כדי לקבוע דגלי מיקום או לנקות ערכים בזמן המעבר.
 ניתוק השיחה
 type: "hangup" 
 מנתק את השיחה מיידית. הפשוט ביותר — שולחים ומנתקים.
 {
 "type" : "hangup" 
}
 לאחר הניתוק תגיע עוד פנייה לשרת עם PBXcallStatus=HANGUP —
 ניתן להשתמש בה לפעולות סיכום שיחה.
 השמעת כל הקמפיינים
 type: "playAllCampaigns" 
 משמיע למתקשר את כל הודעות הקמפיינים שנשלחו אליו.
 ניתן לקבוע כמה ימים אחורה לחפש הודעות — אם לא צוין, ברירת המחדל היא שנה (365 ימים).
 פרמטר חובה? ערך הסבר 
 type חובה "playAllCampaigns" סוג המודול 
 daysBack רשות מספר ימים כמה ימים אחורה להשמיע קמפיינים. ברירת מחדל: 365 
 {
 "type" : "playAllCampaigns" ,
 "daysBack" : 30 // השמעת קמפיינים מ-30 הימים האחרונים 
}
 אם לא מועבר daysBack , יוצגו קמפיינים מהשנה האחרונה (365 ימים).
 השמעת הקמפיין האחרון
 type: "lastCampaign" 
 משמיע למתקשר את הקמפיין האחרון שנשלח . ניתן לבחור לפי מה לאתר את הקמפיין,
 ואף לדרוס את הטלפון/המחוייג המשמשים לחיפוש — למשל להשמיע את הקמפיין האחרון שנשלח למספר שנאסף בשיחה.
 פרמטר חובה? ערך הסבר 
 type חובה "lastCampaign" סוג המודול 
 playBy אופציונלי 
 phone לפי טלפון מקבל ההודעה (ברירת מחדל)
 did לפי המספר המחוייג — הקמפיין האחרון על אותו מספר

 לפי מה לאתר את הקמפיין

 סליקת אשראי
 type: "creditCard" 
 מבצע סליקת כרטיס אשראי מול הסולק (Nedarim Plus) באמצע תזרים API.
 אוסף מהמתקשר את פרטי הכרטיס (מספר, תוקף, ואופציונלית CVV / ת"ז / מספר תשלומים),
 שולח לסולק, ומחזיר את התוצאה (סטטוס + מספר אישור) לקריאה הבאה לשרת שלכם.
 אבטחה: מספר כרטיס מלא, CVV ותעודת זהות לא נשמרים אצלנו.
 נשמרים רק 4 ספרות אחרונות, תוקף, סכום, סטטוס ומספר אישור — לכל ניסיון, גם בכשל.
 שדות מערכת
 פרמטר חובה? ערכים הסבר 
 type חובה "creditCard" סוג המודול 
 name חובה טקסט שם לוגי. תחתיו יוחזרו הסטטוס ומספר האישור (ראו "מה חוזר") 
 fixed אופציונלי "yes" / "no" "yes" = שמירת הערכים שחזרו לפנייה הבאה (ברירת מחדל "no" ) 
 פרמטרי סליקה
 פרמטר ברירת מחדל הסבר 
 sum 0 סכום לחיוב. 0 = יבקש מהמתקשר להזין סכום 
 sumChangeable "no" "yes" = משמיע את הסכום ומבקש אישור (1 = אישור, *0 = ביטול) 
 cvv "yes" "yes" = יבקש 3-4 ספרות CVV 
 tz "yes" "yes" = יבקש תעודת זהות (6-9 ספרות) 
 payments 1 מקסימום תשלומים. 1 = לא ישאל. >1 = ישאל בין 1 ל-X 
 paymentsMode "regular" אופן פריסת התשלומים בסולק (Nedarim Plus):
 "regular" = חיוב רגיל (תפיסת מסגרת אשראי).
 "keva" = פריסה כ הוראת קבע ללא תפיסת מסגרת (DebitKeva) — מתאים לעסקת תשלומים.
 "ask" = המתקשר בוחר בשיחה בין השניים (1 = רגיל, 2 = הוראת קבע ללא תפיסת מסגרת).
 "kevaMonthly" = הקמת הוראת קבע לפי סכום חודשי קבוע — הסכום
 ( sum , או מה שהמתקשר הקיש) הוא הסכום החודשי , לא סכום כולל.
 ללא הגבלת מספר חודשים (עד ביטול), אלא אם נשלח kevaMonths . לא נשאלת שאלת תשלומים.
 פעיל בעיקר כש- payments>1 (למעט "kevaMonthly" ); עם תשלום בודד הסולק חוזר אוטומטית לחיוב רגיל. 
 kevaMonths "" רק ל- paymentsMode="kevaMonthly" : סך מספר החיובים החודשיים.
 ריק / 0 = הוראת קבע ללא הגבלת חודשים (עד ביטול) 
 kevaDay "" רק ל- paymentsMode="kevaMonthly" : יום החיוב בחודש (1-28).
 ריק = היום בחודש שבו בוצעה השיחה 
 category "" קטגוריה לסולק (טקסט חופשי, נתמך בעברית) 
 terminal "" מסוף בסולק 
 chargeMode "" record = רישום תשלום בלבד, ללא חיוב: המתקשר בוחר סכום ומאשר (ומספר תשלומים, כש- payments גדול מ-1), בלי הקשת פרטי כרטיס. עם askDay=yes המתקשר בוחר גם יום גבייה בחודש (1-28) — לרישום בלבד, ללא גבייה אוטומטית. מספר האישור המוחזר הוא מספר הרישום. ריק = חיוב רגיל באשראי 
 דגלי השמעה (אופציונליים) — מה המתקשר שומע
 פרמטר אם "yes" 
 noSum משתיק את ההכרזה "הסכום לתשלום הוא X" — רק כש- sumChangeable=no 
 noSuccess משתיק את "העסקה נקלטה בהצלחה" 
 noConfirmation משתיק את "מספר האישור הוא X" + הקראת הספרות 
 noFailExit בכשל לא יוצא מהמודול — חוזר שוב ושוב לבקש פרטי כרטיס עד הצלחה. אין שום מקש יציאה. 
 זהירות עם noFailExit=yes : המתקשר נתקע בלולאה עד שיצליח לסלוק או ינתק.
 השתמשו רק כשהשיחה לא יכולה להמשיך בלי סליקה מוצלחת.
 פריסת תשלומים — הוראת קבע ללא תפיסת מסגרת: בעסקת תשלומים אפשר לבחור
 (דרך paymentsMode ) שהחיוב ייפרס כ הוראת קבע ללא תפיסת מסגרת אשראי במקום
 חיוב רגיל שתופס את מלוא המסגרת. אפשר לקבע זאת מראש ( "keva" ) או לתת
 ל מתקשר עצמו לבחור בשיחה ( "ask" ) בין חיוב רגיל לבין הוראת קבע ללא תפיסת מסגרת.
 הוראת קבע לפי סכום חודשי קבוע ( "kevaMonthly" ): בשונה מ- "keva" 
 (שפורס סכום כולל לתשלומים), כאן הסכום שנקבע או שהמתקשר מקיש הוא הסכום החודשי הקבוע ,
 וההוראה נמשכת ללא הגבלת מספר חודשים עד ביטול. אפשר להגביל את מספר החיובים עם
 kevaMonths ולקבוע את יום החיוב בחודש עם kevaDay . שאלת מספר התשלומים לא מושמעת במצב זה.

 תזרים השיחה למתקשר
 השמעת/אישור סכום (אם רלוונטי)
 בקשת מספר כרטיס (9-16 ספרות)
 בקשת תוקף (4 ספרות, MMYY) — בדיקת תקינות, מבקש שוב אם פג
 CVV — אם cvv=yes 
 תעודת זהות — אם tz=yes 
 מספר תשלומים — אם payments>1 (לא נשאל ב- paymentsMode="kevaMonthly" )
 בחירת אופן החיוב — רק אם paymentsMode="ask" : "לחיוב רגיל הקש 1, להוראת קבע ללא תפיסת מסגרת הקש 2" ( *0 = ביטול)
 שליחה לסולק וקבלת תשובה
 הצלחה: אישור + מספר אישור + תפריט סיום ( 1 = סליקה נוספת, *#0 = יציאה)
 כשל: הודעת שגיאה. אם noFailExit=yes חוזר לשלב 2; אחרת יוצא מהמודול
 מה יחזור לשרת בקריאה הבאה (לפי name="payment" ):
 payment = OK / ERROR / סטטוס שחזר מהסולק (כגון DECLINE )
 CONFIRM_payment = מספר האישור (ריק בכשל)
 ?...&payment=OK&CONFIRM_payment=12345678&...
 ערכי סטטוס
 ערך משמעות 
 OK הסליקה הצליחה 
 ERROR המתקשר ביטל (*/0), נתק, או תקלה כללית 
 אחר סטטוס שחזר ישירות מהסולק (לדוגמה DECLINE ) 
 תיעוד אוטומטי: כל ניסיון סליקה (הצלחה או כשל) נרשם אצלנו עם הסטטוס,
 מספר האישור, סכום, מספר תשלומים, 4 ספרות אחרונות, תוקף, וכל פרמטרי המודול ב-JSON.
 מספר כרטיס מלא / CVV / ת"ז לא נשמרים.

 טקסט — Text-to-Speech
 { "text" : "שלום, ברוכים הבאים לחברת XYZ" }
 המערכת תקריא את הטקסט בקול. ברירת המחדל היא קול גוגל סטנדרטי he-IL-Standard-D — ללא עלות נוספת . ניתן לבחור קול אחר ע"י הוספת voice (בתוספת תשלום — ראו "בחירת קול הקראה" למטה).
 טיפ — מומלץ להשתמש במקטעי טקסט קצרים ולא במשפט אחד ארוך. 
 כל מחרוזת text ייחודית מתומללת פעם אחת ע"י מנוע ה-TTS, ומאז נשמרת בקאש.
 השמעות חוזרות של אותה מחרוזת בדיוק — מוגשות מהקאש מיידית וללא חיוב נוסף 
 (חשוב במיוחד עבור קולות Gemini בתשלום, שמחויבים פר תמלול).
 הכלל המעשי: פצלו פרומפט ארוך לכמה פריטי text קצרים ושמישים-לשימוש-חוזר,
 במקום פסקה אחת ארוכה. ככה שינוי קטן באחד המשפטים לא מאלץ תמלול חוזר של כל הטקסט,
 ומשפטים זהים שחוזרים על עצמם בין שיחות / תפריטים — מוגשים תמיד מהקאש.
 ❌ פחות יעיל — בלוק אחד ארוך וייחודי:
